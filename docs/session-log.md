2026-10-12, 16:29, [BUGFIX] Frame cost grew with distance explored: 110 -> 55 -> 30-40 fps over a long walk, never recovering. Three compounding causes: (1) updateChunks() only ever added to `chunks`, so every chunk ever visited stayed resident; (2) the draw loop submitted ALL of them every frame with no distance and no frustum culling, so geometry per frame grew linearly with distance walked; (3) all 16 vertical layers were always loaded and meshed (9*9*16 = 1296 chunks, most of them pure air above the terrain), each with a VAO, a VBO and a draw call. Adopted the Minecraft model, which splits the two lifetimes that matter: `chunks` is the world's Cells, created on first touch and never discarded, while `meshedChunks` is only the subset currently holding GPU memory - leaving releases the VAO/VBO and keeps the Cells, returning re-meshes from the same data. World generation had to become reproducible for that to hold, because otherwise walking away would rearrange the world behind the player and sprout trees inside new builds: terrain already was (Perlin noise is a pure function of position) but trees drew from Math.random(). Tree decisions (existence, trunk height, canopy corner trimming) now come from WorldGen.Random seeded by a hash of the chunk's own grid position. Also: vertical reach is +-3 chunks instead of all 16 layers; an all-air chunk gets no GPU object and no draw call; meshing is rationed to 8 chunks per frame so crossing a boundary fills in over a couple of frames instead of stalling; chunk lookup now generates on demand and returns null ONLY for "outside the world", never "not loaded yet" - with a finite vertical band the old null-to-air reading would have let physics and the raycast see straight through ground the streamer had not reached; safeSpawn() now runs before the first streaming pass so the world is not meshed around the default spawn height and then thrown away; cleanup() releases every live mesh before the context dies.

2026-10-13, 16:25, [BUGFIX] Minimap player marker grew as the player looked up or down, eventually covering half the disc. Cause: the shader sizes the facing tick by measuring a fragment's perpendicular distance from the heading vector and its distance along it, and both of those tests are only meaningful for a UNIT vector - hand them one of length L and the tick comes out L times too wide and L times too long. It was being handed player.front's raw x and z, and front is a normalised *3D* direction whose horizontal part is cos(pitch): level 1.0, 60 degrees 0.5, 89 degrees 0.0175. So the marker's size was 1/cos(pitch), and at full upward gaze the perpendicular tolerance alone was 0.69 against a disc of radius 0.5 - the tick was wider than the map. That is exactly the reported "thickens, then swallows half the map", and it explains why it appeared to worsen the longer you looked: pitch does not return to level on its own. Fixed by normalising the horizontal component and dropping pitch entirely, which is also the correct reading of a heading on a plan view - a top-down map has no vertical component to show. The degenerate case needs state to handle honestly: looking straight up or down has no horizontal direction at all, so Minimap keeps the last heading that had one and the marker holds still instead of spinning or reporting a vector of zeros (a virgin map with no prior heading falls back to north, which is a guess the map admits to by having no better answer). Regression test sweeps all 179 reachable pitches and asserts the heading stays unit length, plus the hold-still and virgin-fallback cases. My first attempt at that sweep failed and the code was right: I seeded worstLength to 0f, so its deviation of 1 outranked every real reading and the "worst" it reported was my own sentinel. Mesher figures unchanged.

2026-10-13, 17:40, [FEATURE] Sounds: five synthesized Occasions (footstep, break, place, pickup, landing) across four Materials (earth, stone, wood, foliage), via OpenAL. No audio files exist in the repo and there is no WAV parser, by design - see docs/adr/0002. Design settled by grilling: OpenAL over javax.sound because positional audio is most of what sound is FOR in a first-person game and javax.sound has none of it; runtime synthesis over committed WAVs because these are placeholders and a parser would be building for a future nobody has chosen yet; grass and dirt share one Material rather than each Block Type getting its own voice, so adding a Block Type is a one-line change. Player now reports landings through a passive consumeLanding() seam rather than a callback, keeping Player ignorant of sound; the same pattern as SolidWorld, and the reason the landing behaviour is testable at all. Break and place sounds sit INSIDE breakBlock/placeBlock after their early returns, so striking bedrock is silent rather than a thud for something that did not happen.

Three real bugs found while building, two of them by running rather than reading. (1) MAX_SECONDS.toInt() truncates 0.45 to 0, making the length clamp an empty range that throws - the very first Synth.render call crashed. Multiply before rounding. (2) fallDistance was reset on the same frame the landing was reported, so every landing reported 0.0 and scaled its own sound to nothing. Captured before the reset. (3) The most interesting: the landing seam reported a landing every few frames while the player stood still. Not a seam bug - the physics. Collision resolves against the DESTINATION, so a fast arrival stops wherever the previous step left it (measured: a 12-block drop lands reporting 8.9, at feet=1.275 instead of ~1.01) and then keeps falling in 0.2-block increments, each a genuine airborne transition. The 2-block threshold was silently absorbing this; the test that caught it asserted something untrue. Moved the threshold into Player as MIN_FALL_TO_LAND, suppressing the report at the source, because a caller that forgets the rule gets a machine gun of landing noises. This is a pre-existing physics wobble, not one introduced here - worth knowing that the game's physics never fully settles.

Verification: 20 new headless assertions, and audio turns out to be unusually checkable - synthesis is just math, so the checks assert no buffer is silent (RMS floor), none clips (peak <= 1), all end at exactly zero so they cannot pop, all are distinct from one another, and that different Materials produce measurably different brightness (zero-crossing centroid: stone brighter than earth, foliage brighter than wood, no two within 20Hz). Determinism is asserted first because if it fails every other sound assertion is testing a moving target. NOT VERIFIED: nothing has been heard. Whether these sound like earth, stone, wood and leaves is exactly the judgement I cannot make, and it is the main thing a playtest has to settle.
